# Daily Workflow：每日「喂文档 → 出建议」详细流程

## 输入形态

用户每次喂入的可能是：
- 一份工作文档（PRD / 评审纪要 / code review / 需求拆分 / Bug 复盘）
- 一段聊天/会议片段（产品讨论 / 技术对齐 / 1v1 反馈）
- 用户口语描述（"今天我做了 xxx"）
- 多份混合

## 处理流程

### Step 1: 读现状

按需读，不要全读：

1. 必读：`<wiki_root>/00_INDEX.md`
2. 根据输入信号词，定位 1-2 个相关层
3. 只读相关层的具体文件

### Step 2: 解析输入

对输入逐段标注：
- 主要信号词（参考 `wiki_taxonomy.md`）
- 落点层（最多 2 层）
- 是更新已有条目还是新增

### Step 3: 输出 4 件套

**严格按以下 schema 输出**，不要遗漏任何一件，不要变更顺序。

```markdown
## 1. 切入点定位

- [更新] 02_Agent产品设计/核心链路.md § Prompt 构造
  - 新增"角色一致性约束"小节
  - 来源：今日 PRD 第 3 节
- [新增] 03_前后端研发/记忆系统.md
  - 初版结构：短期记忆窗口 / 长期记忆 vector / 检索策略
  - 来源：技术对齐会议
- [候选 case] 04_Case故事库/case_困难闭环_角色漂移.md
  - 暂不落地，等下周 AB 数据回来再升级

## 2. 今日「我做了什么」（增强版 STAR）

- **S（背景）**：用户在多轮对话里反馈角色「不像那个角色了」，用户自定义角色 D7 留存比官方角色低 8pp
- **T（目标）**：在两周内把角色漂移率从 X% 降到 Y%，覆盖 top 50 自定义角色
- **A（过程）**：
  - 分析：抽样 200 条漂移对话，归因到「记忆截断」+「prompt 优先级冲突」
  - 方案：A=加长上下文窗口；B=加 RAG 检索人设知识；C=system prompt 重排
  - 取舍：B 成本可控且可灰度，A 成本爆炸，C 短期收益小 → 选 B
  - 推进：拉算法对齐人设知识抽取规则，前端做加载态，灰度 5% 用户
- **R（结果）**：观察中。漂移率初步从 12% 降到 7%（小流量），D7 留存预计 2 周后回归。

> mentor 视角推测点评：可能会问「为什么不是先做 prompt 重排，成本最低」？建议准备好"灰度数据已显示 prompt 重排在 top 50 角色上效果不显著"的回答。?

## 3. 可深挖 / 多做的建议

- **数据**：补一份「漂移率按角色类型分布」的数据，证明方案对所有类型都有效
- **认知盲点**：对照 [01_行业认知/竞品地图.md] 看看 Character.AI 和星野是怎么处理这个问题的
- **高光点**：本次决策可升级为 case 故事 A（困难闭环型）— 关键词「角色漂移方案」
- **写作建议**：在 02_Agent产品设计/决策记录.md 立即登记本次决策（4 维表格）

## 4. TODO 清单

### 待问 mentor
- [ ] 这个方案 PM/算法 Lead 是否同意「成本可控」的判断？
- [ ] AB 跑多久才能定论？

### 待跑数据 / 待补素材
- [ ] SQL：按角色类型拆分的漂移率
- [ ] 截图脱敏：灰度面板 + 留存看板
- [ ] 用户原话：从客诉系统抽 5 条典型反馈

### 待复盘 case
- [ ] 等灰度结束后升级为 case_困难闭环_角色漂移.md
- [ ] 准备 3 个高频追问的答案

## 5. 是否按上述方案写入 wiki？

请回复：
- "全部确认" — skill 写入所有 [更新]/[新增] 项
- "确认 X、Y" — 只写其中几条
- "改一下" — 描述需要怎么调整
- "暂不写入" — 只看 4 件套，不动文件
```

### Step 4: 等用户确认

收到确认后才动手。**绝对不要先写后问**。

### Step 5: 执行写入

- **更新已有文件**：用 `Edit` 工具，精准定位章节，加新内容到合适位置
- **新建文件**：用 `Write` 工具，必须基于 `assets/entry_templates/` 对应模板（按层取）
- **每次写入末尾追加溯源**：
  ```
  > 更新源：2026-04-26 今日 PRD 第 3 节 + 技术对齐会议
  ```
- **同步更新 INDEX**：在 `00_INDEX.md` 对应层下登记新条目，已有条目更新"最近修改时间"

### Step 6: 写完后给用户一份变更清单

```markdown
✅ 已写入：
- 02_Agent产品设计/核心链路.md（追加"角色一致性约束"小节）
- 03_前后端研发/记忆系统.md（新建，初版 180 字）
- 00_INDEX.md（同步更新）

⏸ 已记录但未写入：
- case_困难闭环_角色漂移.md → 标记为候选，待数据回归

📋 你的下一步动作（高 ROI 排序）：
1. 跑那条 SQL（漂移率拆分）— 这是最重要的数据补强
2. 找 mentor 1v1 对齐"成本可控"判断
3. 周五前把 case 草稿写完
```

## 输出格式约束

- **数据带 ?**：所有推测/估计的数据后面加 `?`，让用户知道这不是事实
- **不写空话**：每条建议都要具体到"做什么动作"，不要写"加强对竞品的关注"这种废话
- **节制 STAR**：今日 STAR 的 S/T/A/R 每段不超过 3 句话。要扩写时让用户决定升级为 case
- **保留人话**：用户原话里有真实细节（如同事名字、具体数据、原始用词），保留下来，不要全部"产品化"

## 边界情况

### 情况 1：输入完全不是工作上下文

如果用户喂的是闲聊或与实习无关的内容，**不要硬套模板**。直接说：

> 这段内容看起来不像实习工作上下文，要继续推进 wiki 更新吗？还是你想做别的事？

### 情况 2：输入信息量太少

少于 200 字且没有具体决策/技术/数据时，先问用户：

> 这段信息我能识别到的落点比较窄。你想：
> A) 我先问你 3 个问题补充一下，再做切入点定位？
> B) 直接把这段标记为「碎片」放到 INDEX 待补区？
> C) 跳过本次更新？

### 情况 3：信息涉及保密内容

如果用户输入里出现 token、密钥、内部用户 ID、未公开战略数据等，**不要写进 wiki**。提醒用户：

> 这段里包含敏感信息（xxx），写 wiki 时建议脱敏。我帮你脱敏后再确认入库吗？
