# Wiki 分层与切入点判定规则

## 4 层定义

| 层 | 关注 | 典型条目 |
|---|---|---|
| 01 行业认知 | 业务在行业里的位置、赛道、用户、竞争、政策 | 业务背景、北极星指标、竞品地图、用户画像、行业关键词、政策风险 |
| 02 Agent 产品设计 | 产品形态、玩法、链路、决策、Eval、商业化 | 产品形态、核心链路、决策记录、Prompt 设计、Eval 框架、商业模式 |
| 03 前后端研发 | 系统架构、接口、模块、工程、性能 | 系统架构、关键接口、记忆系统、人设引擎、对话状态机、灰度与监控 |
| 04 Case 故事库 | 可口述的 2-3 分钟故事 | case_困难闭环_xxx、case_认知反转_xxx |

## 切入点判定（信号词 → 落点层）

读到一段输入文档时，先扫信号词，决定主要落点层。

### → 01 行业认知

- 用户研究 / 用户画像 / 调研访谈
- 竞品 / 对标 / benchmark / 友商 / 同类产品
- 行业 / 赛道 / 市场 / 增长趋势
- 北极星 / DAU / MAU / 留存 / LTV
- 政策 / 合规 / 监管 / 安全要求

### → 02 Agent 产品设计

- 需求评审 / PRD / 功能设计 / 产品方案
- 玩法 / 卡牌 / 人设 / 世界观 / 剧本
- 决策 / 取舍 / 方案对比 / 评审结论
- Prompt / system prompt / few-shot
- AB / Eval / 评测 / 评分
- 付费 / 订阅 / 虚拟物品 / 充值

### → 03 前后端研发

- 架构 / 服务 / 模块 / 链路 / 调用关系
- 接口 / API / 协议 / 数据模型 / DB / Schema
- 部署 / CI / 灰度 / 监控 / 报警 / 日志
- 性能 / 延迟 / QPS / 成本 / token 用量
- Bug / 异常 / 故障 / 复盘
- 缓存 / 队列 / 流式 / 并发

### → 04 Case 故事库（候选）

只要输入里出现以下词且**伴随用户主语视角**（"我推动""我说服""我后来发现"），就标为候选 case：

- 推不动 / 卡了好久 / 跨团队 / 没人接
- 翻盘 / 反转 / 之前判断错 / 后来才发现
- 最终结果 / 上线后 / 数据证明 / AB 拉胜
- 学到了 / 想通了 / 形成方法论

## 冲突处理原则

### 原则 1：最具体落点优先

一段话同时涉及"产品决策"和"工程实现"，优先落到更具体的那条：
- 决策本身（为什么这么选）→ 02
- 实现细节（怎么做的）→ 03

### 原则 2：跨层时拆条目，不合并

如果一段话同时有「行业洞察 + 产品决策」，拆成两条切入点，分别更新两个文件，互相用 Obsidian 双链 `[[xxx]]` 关联。

### 原则 3：Case 是"投影"不是"搬运"

case 故事里出现的产品/技术细节，**应该已经在 02/03 层有条目**。case 文件用双链指向那些条目，不要把整段技术描述复制进 case。

### 原则 4：决策记录 vs Case 的区分

| 决策记录（02 层） | Case 故事（04 层） |
|---|---|
| 客观描述：方案 A vs B vs C，选了 B | 主观叙事：我怎么推动，遇到什么阻力，结果如何 |
| 重点是"取舍逻辑" | 重点是"个人贡献和成长" |
| 写完就稳定 | 会反复打磨，准备口述 |

一个事件可以同时落在 02 和 04，互为补充。

## 切入点表达格式（Daily Workflow 输出用）

```
- [更新] 02_Agent产品设计/核心链路.md § Prompt 构造 — 新增"角色一致性约束"小节
- [新增] 03_前后端研发/记忆系统.md — 基于今日讨论初版
- [候选] 04_Case故事库/case_困难闭环_长记忆.md — 等数据回归后升级
```

格式要点：
- `[更新]` / `[新增]` / `[候选]` 三种标签
- 路径 + 章节锚点（用 `§ 章节名`）
- 后接 `— ` 加一句说明这次改了什么

## 从输入识别条目的工作步骤

1. 通读输入，标记每个段落的信号词
2. 对每段确定主要落点层（最多 2 层）
3. 在该层目录下找最匹配的现有条目（先看 INDEX，再看具体文件）
4. 没有现有条目时，按本文件的"典型条目"列表里挑最近的，或新建
5. 输出切入点清单时，按 `01 → 02 → 03 → 04` 顺序排列
